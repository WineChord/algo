# 题解写作模板

好的题解不是代码说明书，而是一条可以复走的推理路径。下面的结构适合绝大多数算法题，可按题目特点增删。

## 0. 可展开的题目入口

专题页和题解索引中的每道在线评测题都使用默认折叠的详情块。读者点击题目标题后，至少能看到简要题意、核心思路、复杂度、原题链接和可提交的完整 C++ 实现。

```markdown
??? problem "平台与编号 · 题目名称"
    [打开原题](https://example.com/problem){ .problem-source }

    **题意**：用一两句话重新表述任务。

    **思路**：说明关键模型、不变量或状态转移。

    **复杂度**：时间 \(O(\cdot)\)，额外空间 \(O(\cdot)\)。

    **C++ 实现**

    ```cpp
    // 完整、可提交、无空行的竞赛风格实现
    ```
```

同一道题若出现在多个知识节点，复用 `includes/problems/` 中的唯一详情片段，避免代码和复杂度说明分叉。

## 1. 题目信息

- 可点击的原题链接；
- 平台、编号、难度；
- 输入规模与关键约束；
- 核心标签，但避免提前泄露全部结论。

## 2. 重新表述问题

用一两句话去掉故事背景，明确要在什么对象上求什么结果。必要时说明容易混淆的术语，例如子数组与子序列、路径与游走。

每日档案中的单题页还要在算法分析之前提供自包含的完整题面层：可点击的官方来源、完整任务定义、输入、输出、全部约束、全部样例和必要注释。AtCoder 常规题在没有题目专属开放许可时，使用独立组织的完整英文呈现并标明版权边界；Codeforces 题遵循其材料使用许可，在题面附近保留来源、原题直链与许可说明。官方链接用于核验和延伸阅读，不应成为理解题目的必经跳转。

## 3. 样例与边界

手动走一遍最能暴露结构的样例，并补充：

- 最小输入；
- 无解或多解；
- 答案位于边界；
- 重复值、负数、零和极值。

## 4. 朴素解

写清：

1. 枚举了哪些维度；
2. 为什么覆盖全部答案；
3. 时间和空间复杂度；
4. 在当前约束下为什么超时或仍可接受。

朴素解有助于找到瓶颈，也可以成为随机对拍的基准实现。

## 5. 优化过程

每一步优化都回答：

- 重复计算或冗余状态是什么；
- 使用了哪条结构性质；
- 新增了什么预处理或数据结构；
- 复杂度从什么降到什么；
- 哪个约束是算法成立的前提。

不要从 $O(n^3)$ 直接跳到最终代码，中间真正值得迁移的是“为什么能少枚举一维”。

## 6. 最优解与证明

先用伪代码或分步骤文字描述，再给 C++ 完整实现。证明应围绕不变量、归纳、交换论证或反证展开。

代码之后明确：

- 时间复杂度；
- 额外空间复杂度；
- 整数范围；
- 最容易出错的边界。

## 7. 多个最优解

若存在同阶方案，逐项比较：

| 维度 | 方案 A | 方案 B |
| --- | --- | --- |
| 正确性证明 |  |  |
| 时间常数 |  |  |
| 额外空间 |  |  |
| 实现稳定性 |  |  |
| 可扩展性 |  |  |

最后明确推荐优先记忆哪一个，以及另一个方案在什么条件下更合适。

## 8. 追问与变种

从约束出发改变条件：

- 数据从静态变动态；
- 只求值变为恢复方案；
- 单次询问变多次询问；
- 非负数变为允许负数；
- 树变图、有向变无向；
- 求任意解变为计数或字典序最小；
- 内存更紧或数据规模更大。

有对应在线评测题时附原题链接，并说明它与主问题究竟改变了什么，而不是只罗列题号。

## 9. 最终复盘

用三句话收束：

1. 识别信号；
2. 核心不变量或状态；
3. 以后遇到什么变化应换用其他算法。
