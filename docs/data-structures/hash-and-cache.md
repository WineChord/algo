# 哈希分组、滑动窗口与 LRU

哈希表并不自动带来线性复杂度。真正决定算法的是键表达了什么等价关系、值保存了哪些未来需要的信息，以及旧状态何时失效。

## 用规范签名表示等价类

字母异位词分组的关系是：26 个字母频次逐项相等。排序后的字符串是通用签名；固定小写字母集时，频次数组避免了每个字符串内部排序。

--8<-- "includes/problems/lc-49.md"

从逐组比较到频次签名的优化过程：

1. 每个新串与已有组代表两两比较，最坏 $O(n^2L)$；
2. 排序串作为键，时间 $O(\sum |s_i|\log|s_i|)$；
3. 26 维计数作为键，平均时间 $O(S+26n)$。

签名必须无歧义。把计数直接拼成十进制数字会让 `[1,11]` 与 `[11,1]` 碰撞；加入分隔符、定长二进制编码或自定义 `array<int,26>` 哈希都可以。

若输入在线到达，分组表无需重建；每次构造一次签名并追加到对应桶。若只求异位词对数量，新串所在桶此前有 $c$ 个元素时，答案增加 $c$。

## 滑动窗口：状态必须精确描述当前区间

最长无重复子串可以让哈希状态保存窗口内频次，也可以保存每个字符最后出现的位置。最后位置版本把左边界直接跳到冲突字符之后。

--8<-- "includes/problems/lc-3.md"

处理右端点 $r$ 前，窗口 `[l,r-1]` 无重复。若当前字符最近位置为 $p$：

- $p<l$ 或未出现：窗口仍合法；
- $p\ge l$：任何包含 $p$ 与 $r$ 的窗口都非法，最小合法左端为 $p+1$。

所以更新必须是 `l = max(l, p + 1)`，不能让左端倒退。两个线性版本的取舍：

- 频次数组：更容易推广到“每种字符至多出现 $k$ 次”；
- 最后位置：本题状态更小、跳跃更直接。

UTF-8 文本不能把一个字节当作一个字符。若题意按 Unicode 码点或用户可见字符定义，必须先按同一规范解码、归一化，再选择哈希键。

## LRU：哈希负责定位，链表负责顺序

缓存同时需要两种操作：

- 按键在期望 $O(1)$ 找到节点；
- 在 $O(1)$ 时间把命中节点变成最新，并删除最旧节点。

单独的哈希表没有时间顺序，单独的链表无法按键常数定位；二者组合才满足接口。

--8<-- "includes/problems/lc-146.md"

核心不变量：

1. 链表从头到尾按最近使用时间由新到旧；
2. 哈希表恰好包含缓存中的所有键，并指向唯一链表节点。

命中的 `get` 与更新已有键的 `put` 都要移动节点；只在 `put` 新键时更新顺序会错误淘汰。`list::splice` 移动节点后迭代器仍有效，适合这里的稳定引用。

### 从模拟到最优

- 顺序数组保存键值与时间：查找或移动为 $O(capacity)$；
- `list + unordered_map`：每次操作期望 $O(1)$；
- 手写双向链表：复杂度相同，哨兵节点可减少头尾特判。

### 约束变化

- 带 TTL：在 LRU 之外增加过期时间堆，并用版本号跳过旧事件；
- 按字节容量：节点保存权重，超限时反复淘汰尾部；
- 并发缓存：必须把哈希、链表和容量更新放在同一同步协议内；
- LFU：排序键从“最近一次时间”变为“频次优先、同频内再按最近使用”，需要频次桶。

## 设计哈希状态的四个问题

1. 哪些对象应落入同一个键？
2. 键是否无歧义、稳定且与题目字符语义一致？
3. 值保存一个位置、全部位置、频次，还是稳定节点引用？
4. 状态何时过期，删除或移动时哪些结构必须同步更新？

回答这四问后，复杂度分析才有意义；“用了哈希表所以 $O(n)$”不是证明。
